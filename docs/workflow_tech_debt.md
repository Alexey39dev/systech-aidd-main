# Workflow устранения технического долга

> Правила выполнения работ по [tasklist_tech_dept.md](tasklist_tech_dept.md) для улучшения качества кода

## 🎯 Основные принципы

- **Качество превыше скорости** - код должен быть правильным, а не быстрым
- **Тесты перед рефакторингом** - защита от регрессии обязательна
- **Одна итерация = одна цель** - не смешивать разные типы улучшений
- **Проверка после каждого изменения** - `make quality` после каждой итерации
- **Маленькие коммиты** - каждая итерация = отдельный коммит с clear message

## 📋 Алгоритм работы над технической задачей

### 1. Выбор итерации улучшения
- [ ] Определить следующую итерацию из `tasklist_tech_dept.md`
- [ ] Проверить, что предыдущая итерация завершена
- [ ] Убедиться в понимании всех требований
- [ ] Проверить baseline метрики (покрытие, lint, type-check)

### 2. Анализ текущего состояния
- [ ] Запустить `make quality` для baseline
- [ ] Зафиксировать текущие метрики:
  - Покрытие тестами (%)
  - Количество ошибок линтера
  - Количество ошибок типизации
- [ ] Выявить конкретные места для улучшения
- [ ] Оценить объем работы

### 3. Планирование решения
- [ ] Проанализировать архитектурное решение
- [ ] Определить какие файлы будут затронуты
- [ ] Спланировать порядок изменений
- [ ] Определить стратегию тестирования
- [ ] Подготовить примеры кода

### 4. Согласование подхода
- [ ] Представить план рефакторинга
- [ ] Показать примеры улучшенного кода
- [ ] Обсудить потенциальные риски
- [ ] Дождаться одобрения от пользователя

### 5. Реализация с проверками
- [ ] Создать/обновить тесты (если нужно)
- [ ] Выполнить рефакторинг кода
- [ ] Запустить `make test` после каждого изменения
- [ ] Запустить `make lint` для проверки стиля
- [ ] Запустить `make type-check` для проверки типов
- [ ] Обеспечить соответствие всем соглашениям

### 6. Проверка качества
- [ ] Выполнить полную проверку: `make quality`
- [ ] Сравнить метрики с baseline:
  - Покрытие улучшилось или не ухудшилось
  - Ошибок линтера стало меньше
  - Ошибок типизации стало меньше
- [ ] Проверить соответствие `conventions.mdc`
- [ ] Проверить соответствие `vision.md`
- [ ] Убедиться что функционал не сломан

### 7. Обновление документации
- [ ] Обновить docstrings если изменилась сигнатура
- [ ] Обновить README.md если изменился API
- [ ] Обновить `tasklist_tech_dept.md` статус итерации
- [ ] Добавить примечания о результатах

### 8. Фиксация улучшений
- [ ] Сделать коммит с описательным сообщением
- [ ] Указать в коммите метрики улучшения
- [ ] Убедиться что все файлы включены
- [ ] Подготовиться к следующей итерации

## ⚙️ Команды для проверки качества

### Форматирование кода
```bash
make format  # Автоматическое форматирование через Ruff
```

### Проверка стиля
```bash
make lint    # Проверка линтером Ruff
```

### Проверка типизации
```bash
make type-check  # Проверка типов через Mypy
```

### Запуск тестов
```bash
make test    # Все тесты + покрытие
```

### Полная проверка
```bash
make quality  # Форматирование + линтинг + типы + тесты
```

### Локальный запуск для smoke test
```bash
make run     # Запуск приложения для проверки работоспособности
```

## ⚠️ Правила рефакторинга

### Обязательные действия
- **Всегда** запускать тесты перед рефакторингом (baseline)
- **Всегда** рефакторить маленькими шагами с промежуточными тестами
- **Всегда** проверять покрытие после изменений
- **Всегда** запускать `make quality` перед коммитом
- **Всегда** проверять соответствие соглашениям

### Запрещенные действия
- **Нельзя** рефакторить без тестов (защита от регрессии)
- **Нельзя** менять поведение при рефакторинге (только структуру)
- **Нельзя** коммитить код с failing tests
- **Нельзя** игнорировать ошибки линтера или типизации
- **Нельзя** уменьшать покрытие тестами

### Стратегии безопасного рефакторинга

#### 1. Extract Method/Class
```python
# Было: большой метод
def process_data(data):
    # 50 строк кода
    pass

# Стало: разбито на методы
def process_data(data):
    validated = validate_data(data)
    transformed = transform_data(validated)
    return save_data(transformed)
```

#### 2. Replace Magic Numbers/Strings
```python
# Было: хардкод
if status_code == 429:
    retry()

# Стало: константы/enum
if status_code == HTTPStatus.TOO_MANY_REQUESTS:
    retry()
```

#### 3. Introduce Parameter Object
```python
# Было: много параметров
def create_client(api_key, model, temp, max_tokens):
    pass

# Стало: объект конфигурации
def create_client(config: Config):
    pass
```

#### 4. Replace Conditional with Polymorphism
```python
# Было: if/elif chain
if error_type == "rate_limit":
    handle_rate_limit()
elif error_type == "timeout":
    handle_timeout()

# Стало: иерархия классов с единым интерфейсом
error.handle()  # Полиморфизм
```

## 📊 Checklist соответствия соглашениям

После каждой итерации проверять:

### Conventions.mdc
- [ ] **KISS**: Код прост и понятен
- [ ] **1 класс = 1 файл**: Структура соблюдена
- [ ] **Именование**: PascalCase/snake_case/UPPER_SNAKE_CASE
- [ ] **Асинхронность**: Все I/O операции async
- [ ] **Обработка ошибок**: Кастомные исключения, graceful degradation
- [ ] **Документация**: Docstrings + type hints
- [ ] **Форматирование**: Ruff format passed
- [ ] **Линтинг**: Ruff lint passed (0 errors)
- [ ] **Типизация**: Mypy passed (strict mode)
- [ ] **Логирование**: structlog используется правильно

### Vision.md
- [ ] **Минимализм**: Нет лишних зависимостей
- [ ] **Простота**: Нет overengineering
- [ ] **Модульность**: Компоненты независимы
- [ ] **SRP**: Единственная ответственность
- [ ] **Тестируемость**: Код легко тестировать

### Quality Metrics
- [ ] **Coverage**: Не упало, желательно выросло
- [ ] **Ruff**: 0 errors, 0 warnings
- [ ] **Mypy**: 0 errors (strict mode)
- [ ] **Tests**: All passing (100%)

## 🎯 Критерии готовности итерации

Итерация считается завершенной когда:

### Код
- ✅ Все задачи итерации выполнены
- ✅ Код отформатирован (`make format`)
- ✅ Линтер не выдает ошибок (`make lint`)
- ✅ Типизация корректна (`make type-check`)
- ✅ Все тесты проходят (`make test`)

### Качество
- ✅ Покрытие не ухудшилось (или выросло)
- ✅ Соблюдены все соглашения из conventions.mdc
- ✅ Архитектура соответствует vision.md
- ✅ Нет технических долгов в измененном коде

### Документация
- ✅ Docstrings обновлены
- ✅ Type hints добавлены/обновлены
- ✅ README актуален (если менялся API)
- ✅ Прогресс обновлен в tasklist_tech_dept.md

### Фиксация
- ✅ Изменения закоммичены
- ✅ Коммит содержит метрики улучшения
- ✅ Пользователь подтвердил готовность

## 🔄 Iterative Improvement Cycle

```
1. Выбрать итерацию
         ↓
2. Зафиксировать baseline (make quality)
         ↓
3. Спланировать изменения
         ↓
4. Согласовать подход
         ↓
5. Реализовать (маленькими шагами)
         ↓
6. Проверить после каждого шага (make test)
         ↓
7. Полная проверка (make quality)
         ↓
8. Сравнить с baseline (улучшилось?)
         ↓
9. Обновить документацию
         ↓
10. Закоммитить с метриками
         ↓
11. Перейти к следующей итерации
```

## 💡 Best Practices для технического долга

### Приоритизация
1. **Критичное** - Безопасность, баги, ошибки
2. **Важное** - Типизация, тесты, архитектура
3. **Желательное** - Оптимизация, DRY, читаемость

### Измеримость
- Всегда фиксируйте метрики до/после
- Используйте конкретные числа (не "стало лучше", а "+15% coverage")
- Документируйте улучшения

### Коммуникация
- Четко объясняйте зачем нужно улучшение
- Показывайте примеры до/после
- Указывайте выгоды от изменений

### Баланс
- Не увлекайтесь оверинжинирингом
- KISS принцип важнее "красивого кода"
- Улучшения должны решать реальные проблемы

---

> **Помните:** Устранение технического долга - это инвестиция в будущее проекта. Каждое улучшение должно быть измеримым и осознанным.

> **Принцип:** Лучше сделать 5 маленьких улучшений с тестами, чем 1 большой рефакторинг без защиты от регрессии.
