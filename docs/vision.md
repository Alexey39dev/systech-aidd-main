# Техническое видение проекта: LLM-ассистент Telegram-бот

## 1. Технологии

### Основной стек
- **Python 3.11+** - основной язык разработки
- **uv** - управление зависимостями (быстрая альтернатива pip)
- **aiogram 3.x** - асинхронная библиотека для Telegram Bot API с polling
- **openai** - клиент для работы с LLM через OpenRouter
- **make** - автоматизация сборки и запуска проекта

### Дополнительные зависимости
- **pydantic** - валидация данных и настройки конфигурации
- **python-dotenv** - управление переменными окружения
- **structlog** - структурированное логирование

### Принципы выбора технологий
- **Минимализм**: только необходимые зависимости
- **Простота**: легкая настройка и запуск
- **Производительность**: асинхронная архитектура
- **Надежность**: проверенные библиотеки

### Исключенные технологии (для MVP)
- База данных (используем хранение в памяти)
- Docker (усложняет для начальной разработки)
- Веб-интерфейс
- Сложные фреймворки
- Множественные LLM провайдеры (только OpenRouter)

- **Инверсия зависимостей** - легкое тестирование и замена компонентов

- **Отсутствие оверинжиниринга** - никаких абстракций "на будущее"

### Подход к тестированию

## 4. Архитектура проекта

### Основные компоненты

1. **TelegramBot** (`bot.py`)
   - Обработка входящих сообщений
   - Отправка ответов пользователям
   - Управление жизненным циклом бота

2. **LLMClient** (`llm_client.py`)
   - Интеграция с OpenRouter через OpenAI API
   - Отправка запросов к LLM
   - Обработка ответов от LLM

3. **DialogManager** (`dialog_manager.py`)
   - Хранение истории диалогов в памяти
   - Управление контекстом разговора
   - Формирование промптов для LLM

4. **Config** (`config.py`)
   - Загрузка настроек из переменных окружения
   - Валидация конфигурации

5. **Logger** (`logger.py`)
   - Настройка структурированного логирования

### Поток данных
```
Пользователь → TelegramBot → DialogManager → LLMClient → OpenRouter
                ↓
            Ответ ← DialogManager ← LLMClient ← OpenRouter
```

### Принципы архитектуры
- **Простота** - линейный поток без сложных абстракций
- **Модульность** - каждый компонент независим
- **Прямолинейность** - минимум промежуточных слоев

## 5. Модель данных

### Основные структуры данных

1. **Message** (dataclass)
   - `user_id: int` - ID пользователя Telegram
   - `text: str` - текст сообщения
   - `timestamp: datetime` - время сообщения

2. **Dialog** (dataclass)
   - `user_id: int` - ID пользователя
   - `messages: List[Message]` - история сообщений
   - `created_at: datetime` - время создания диалога

3. **Config** (Pydantic модель)
   - `telegram_token: str` - токен бота
   - `openrouter_api_key: str` - ключ OpenRouter
   - `system_prompt: str` - системный промпт
   - `max_history: int` - максимальная длина истории

### Принципы хранения данных
- **В памяти** - простой словарь `{user_id: Dialog}`
- **Без персистентности** - данные теряются при перезапуске
- **Простота** - никаких ORM или сложных схем
- **Минимализм** - только необходимые поля

## 6. Работа с LLM

### Интеграция с OpenRouter
- **Провайдер**: OpenRouter через OpenAI API клиент
- **Модель по умолчанию**: `openai/gpt-3.5-turbo` (баланс цена/качество)
- **Альтернативные модели**: возможность смены через конфигурацию

### Параметры LLM
- **Температура**: 0.7 (баланс креативности и предсказуемости)
- **Max tokens**: 1000 (достаточно для ответов)
- **Top-p**: 0.9 (стандартное значение)

### Формирование промптов
- **Системный промпт** - роль ассистента (из конфигурации)
- **История диалога** - последние N сообщений
- **Пользовательское сообщение** - текущий запрос

### Обработка ответов
- **Простая обработка** - возврат текста ответа
- **Обработка ошибок** - fallback сообщения
- **Лимиты токенов** - обрезка истории при превышении
- **Простые запросы** - без streaming, синхронные вызовы

## 7. Сценарии работы

### Основные сценарии

1. **Запуск бота**
   - Загрузка конфигурации из .env
   - Инициализация компонентов
   - Запуск polling для Telegram

2. **Получение сообщения от пользователя**
   - Получение текста сообщения
   - Добавление в историю диалога
   - Отправка запроса к LLM
   - Отправка ответа пользователю

3. **Обработка команд бота**
   - `/start` - приветствие и описание бота
   - `/help` - справка по использованию
   - `/clear` - очистка истории диалога
   - Обычные сообщения - обработка через LLM

4. **Обработка ошибок**
   - Ошибка LLM → отправка fallback сообщения
   - Ошибка Telegram → логирование и продолжение работы
   - Ошибка конфигурации → остановка с сообщением об ошибке

5. **Очистка истории**
   - При превышении max_history → удаление старых сообщений
   - При перезапуске → полная очистка всех диалогов

## 8. Подход к конфигурированию

### Источники конфигурации
- **.env файл** - основные настройки (токены, ключи)
- **Переменные окружения** - приоритет над .env
- **Значения по умолчанию** - fallback для всех параметров

### Структура .env файла
```
TELEGRAM_BOT_TOKEN=your_bot_token
OPENROUTER_API_KEY=your_api_key
SYSTEM_PROMPT=Ты полезный ассистент
MAX_HISTORY=10
LLM_MODEL=openai/gpt-3.5-turbo
LLM_TEMPERATURE=0.7
LLM_MAX_TOKENS=1000
```

### Валидация конфигурации
- **Pydantic модели** - автоматическая валидация типов
- **Обязательные поля** - проверка наличия критических параметров
- **Значения по умолчанию** - для необязательных параметров
- **Простота** - только .env файл, без сложных конфигурационных схем

## 9. Подход к логгированию

### Библиотека логирования
- **structlog** - структурированное логирование
- **Простота настройки** - минимум конфигурации
- **Читаемость** - понятные форматы логов

### Уровни логирования
- **INFO** - основные события (запуск, получение сообщений)
- **ERROR** - ошибки (LLM недоступен, проблемы с Telegram)
- **DEBUG** - детальная отладка (только при необходимости)

### Форматы логов
- **Консоль** - цветной вывод для разработки
- **JSON** - структурированный формат для продакшена
- **Простота** - без сложных ротаций и файлов

### Что логируем
- Запуск и остановка бота
- Получение сообщений от пользователей
- Запросы к LLM и ответы
- Ошибки и исключения
- Простые логи - без метрик и сложной аналитики

- **Гибкость** - легкая настройка роли ассистента через системный промпт

Все разделы технического видения согласованы и готовы для начала реализации. Проект может быть реализован поэтапно, начиная с базовой функциональности и постепенно добавляя дополнительные возможности.
