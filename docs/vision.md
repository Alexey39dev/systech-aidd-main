## 2. Принцип разработки

### Основные принципы
- **KISS (Keep It Simple, Stupid)** - максимальная простота решения
- **ООП с правилом "1 класс = 1 файл"** - четкое разделение ответственности
- **Минимальный MVP** - только необходимая функциональность для проверки идеи
- **Асинхронность** - использование async/await для производительности
- **Конфигурация через переменные окружения** - простое управление настройками

### Архитектурные принципы
- **Модульность** - каждый компонент независим
- **Инверсия зависимостей** - легкое тестирование и замена компонентов
- **Единственная ответственность** - каждый класс решает одну задачу
- **Отсутствие оверинжиниринга** - никаких абстракций "на будущее"

### Подход к тестированию
- **Покрытие >80%** - высокое покрытие критических компонентов
- **Простота тестов** - без излишне сложных моков и фикстур
- **Фокус на функциональности** - тестируем основные сценарии работы
- **Параметризация** - использование @pytest.mark.parametrize для множества случаев
- **Async тесты** - полная поддержка асинхронного кода

### Подход к качеству кода
- **Автоматизация проверок** - make quality перед каждым коммитом
- **Статическая типизация** - Mypy в strict режиме для всех публичных API
- **Форматирование** - Ruff для единого стиля кода
- **Линтинг** - Ruff для обнаружения ошибок и anti-patterns
- **Измеримость** - метрики качества (покрытие, ошибки линтера, ошибки типов)

## 4. Архитектура проекта

### Основные компоненты

1. **ConsoleApp** (`console.py`)
   - Обработка ввода от пользователя через консоль
   - Вывод ответов в консоль
   - Управление жизненным циклом приложения
   - Обработка команд (/help, /history, /stats, /clear, /role, /exit) ⭐ обновлено
   - Координация между LLMClient, DialogManager и RoleManager ⭐ обновлено

2. **LLMClient** (`llm_client.py`)
   - Интеграция с OpenRouter через OpenAI API
   - Отправка запросов к LLM с retry логикой
   - Обработка ответов от LLM
   - Обработка ошибок API (rate limit, timeout, connection)

3. **DialogManager** (`dialog_manager.py`) ⭐ **ОБНОВЛЕНО (S001)**
   - Управление историей диалога через БД
   - Асинхронные операции (async/await)
   - Добавление и хранение сообщений в PostgreSQL
   - Обрезка истории по max_history (soft delete)
   - Получение статистики диалога
   - Интеграция с DatabaseClient

4. **Config** (`config.py`)
   - Загрузка настроек из переменных окружения
   - Валидация конфигурации через Pydantic
   - Значения по умолчанию для всех параметров

5. **Logger** (`logger.py`)
   - Настройка структурированного логирования через structlog
   - Цветной вывод для консоли
   - Логирование в файл (опционально)

6. **RoleManager** (`role_manager.py`)
   - Загрузка системных промптов из файлов
   - Парсинг метаданных роли (заголовок, описание)
   - Валидация файлов промптов
   - Предоставление информации о текущей роли
   - Поддержка команды `/role`

7. **DatabaseClient** (`database.py`) ⭐ **НОВОЕ (S001)**
   - Управление подключением к PostgreSQL (asyncpg pool)
   - Raw SQL запросы для операций с БД
   - CRUD операции для сообщений:
     - `add_message()` - INSERT с автоматическим подсчетом длины
     - `get_messages()` - SELECT только активных (не удаленных)
     - `soft_delete_message()` - UPDATE deleted_at (soft delete)
     - `clear_all_messages()` - массовое soft delete
   - Параметризованные запросы (защита от SQL инъекций)
   - Lifecycle управление (connect/close)

### Дополнительные компоненты

8. **Exceptions** (`exceptions.py`)
   - Иерархия кастомных исключений
   - AppError, LLMError, ConfigError и др.
   - Улучшение обработки ошибок

9. **RetryUtils** (`retry_utils.py`)
   - Декораторы/функции для retry логики
   - Exponential backoff
   - Конфигурируемые параметры

10. **Messages** (`messages.py`)
   - Константы для сообщений пользователю
   - Enum для ErrorMessages, InfoMessages
   - Централизованное управление текстами

### Типизация

- **Строгая типизация** - все публичные функции имеют type hints
- **Literal types** - для строковых констант (role: Literal["user", "assistant"])
- **Protocol** - для определения интерфейсов компонентов
- **Generic types** - для контейнеров (List[MessageDict], Optional[str])
- **Mypy strict mode** - полная проверка типов

### Схема базы данных (PostgreSQL) ⭐ **НОВОЕ (S001)**

**Таблица `messages`:**
```sql
CREATE TABLE messages (
    id SERIAL PRIMARY KEY,
    role VARCHAR(20) NOT NULL,
    content TEXT NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    length INTEGER NOT NULL,
    deleted_at TIMESTAMP NULL
);
CREATE INDEX idx_messages_deleted_at ON messages(deleted_at);
```

**Поля:**
- `id` - автоинкремент, первичный ключ
- `role` - user/assistant/system
- `content` - текст сообщения
- `created_at` - автоматическая дата создания
- `length` - длина сообщения в символах (вычисляется автоматически)
- `deleted_at` - NULL = активно, NOT NULL = удалено (soft delete)

**Индексы:**
- `idx_messages_deleted_at` - для быстрой фильтрации активных сообщений

### Принципы хранения данных ⭐ **ОБНОВЛЕНО (S001)**
- **PostgreSQL** - персистентное хранение в СУБД
- **Raw SQL** - прямые запросы через asyncpg без ORM
- **Soft delete** - данные не удаляются физически, а помечаются
- **Метаданные** - автоматическое сохранение created_at и length
- **Простота** - минимальная схема БД, одна таблица
- **Типобезопасность** - полная типизация для предотвращения ошибок
- **Асинхронность** - asyncpg для высокой производительности
- **Миграции** - Alembic с raw SQL для контроля схемы

## 6. Работа с LLM

### Интеграция с OpenRouter
- **Провайдер**: OpenRouter через OpenAI API клиент
- **Модель по умолчанию**: `openai/gpt-3.5-turbo` (баланс цена/качество)
- **Альтернативные модели**: возможность смены через конфигурацию

### Параметры LLM
- **Температура**: 0.7 (баланс креативности и предсказуемости)
- **Max tokens**: 1000 (достаточно для ответов)
- **Top-p**: 0.9 (стандартное значение)

### Формирование промптов
- **Системный промпт** - загружается из файла через RoleManager ⭐ **обновлено**
  - Файлы в директории `prompts/`
  - Формат: заголовок роли + описание + промпт
  - Путь задается в конфигурации (SYSTEM_PROMPT_FILE)
  - Альтернатива: прямая строка в SYSTEM_PROMPT
- **История диалога** - последние N сообщений
- **Пользовательское сообщение** - текущий запрос

### Структура файла промпта ⭐ **НОВОЕ**
```txt
# Заголовок роли: Технический ассистент
# Описание: Эксперт технической поддержки для решения проблем

Ты - опытный специалист технической поддержки.
Твоя задача - помогать пользователям решать технические проблемы...
[детальные инструкции для LLM]
```

### Обработка ответов
- **Простая обработка** - возврат текста ответа
- **Retry логика** - до 3 попыток с exponential backoff
- **Обработка ошибок** - специфичные для типа ошибки (rate limit, timeout, connection)
- **Fallback сообщения** - понятные сообщения пользователю при ошибках
- **Лимиты токенов** - обрезка истории при превышении
- **Простые запросы** - без streaming

### Обработка ошибок LLM

**Типы ошибок:**
1. **RateLimitError** - превышен лимит запросов
   - Retry с увеличенной задержкой
   - Сообщение пользователю о необходимости подождать

2. **APIConnectionError** - ошибка подключения
   - Retry до 3 раз
   - Проверка интернет-соединения

3. **APITimeoutError** - таймаут запроса
   - Retry с увеличением timeout
   - Информирование пользователя

4. **APIError (4xx)** - клиентская ошибка
   - Без retry (проблема с запросом)
   - Логирование для отладки

5. **APIError (5xx)** - серверная ошибка
   - Retry до 3 раз
   - Fallback сообщение

**Стратегия retry:**
```python
max_retries = 3
initial_delay = 1.0  # секунды
max_delay = 10.0     # секунды
backoff_factor = 2   # экспоненциальный рост

# Задержки: 1s, 2s, 4s
```

## 7. Сценарии работы

### Основные сценарии

1. **Запуск приложения**
   - Загрузка конфигурации из .env
   - Загрузка системного промпта из файла (RoleManager) ⭐ **НОВОЕ**
   - Инициализация компонентов
   - Вывод приветственного сообщения с ролью ⭐ **НОВОЕ**
   - Запуск цикла ввода/вывода

2. **Получение сообщения от пользователя**
   - Получение текста через input()
   - Добавление в историю диалога
   - Отправка запроса к LLM
   - Вывод ответа в консоль

3. **Обработка команд**
   - `/help` - справка по использованию
   - `/history` - история диалога
   - `/stats` - статистика диалога
   - `/clear` - очистка истории диалога
   - `/role` - отображение информации о текущей роли ⭐ **НОВОЕ**
   - `/exit` - выход из приложения
   - Обычные сообщения - обработка через LLM

4. **Обработка ошибок**
   - Ошибка LLM → вывод fallback сообщения
   - Ошибка конфигурации → остановка с сообщением об ошибке
   - KeyboardInterrupt → graceful shutdown

5. **Управление историей**
   - При превышении max_history → удаление старых сообщений
   - При команде /clear → очистка истории
   - При перезапуске → полная очистка

6. **Просмотр роли ассистента** ⭐ **НОВОЕ**
   - Команда `/role` → запрос к RoleManager
   - Получение метаданных роли (название, описание, источник)
   - Форматированный вывод информации:

## Резюме технического видения

Данный документ определяет техническое видение для создания специализированного LLM-ассистента с консольным интерфейсом. Проект следует принципам KISS и ООП, используя минимальный набор технологий и современные практики качества кода.

**Ключевые характеристики:**
- **Простота** - минимальный MVP без оверинжиниринга
- **Специализация** - конкретная роль через файловые промпты ⭐ **НОВОЕ**
- **Модульность** - четкое разделение ответственности между компонентами
- **Асинхронность** - производительная обработка запросов
- **Гибкость** - легкая настройка и смена роли через файлы промптов ⭐ **обновлено**
- **Консольный интерфейс** - быстрый и удобный доступ через терминал
- **Качество кода** - автоматизированные проверки, типизация, высокое покрытие тестами

**Технологический стек:**
- Python 3.11+ с строгой типизацией (Mypy)
- Ruff для форматирования и линтинга
- pytest с покрытием >80%
- Async/await архитектура
- Pydantic для валидации
- structlog для логирования

**Архитектурные принципы:**
- **SOLID** - Single Responsibility, Open/Closed, Dependency Inversion
- **DRY** - Don't Repeat Yourself (no code duplication)
- **KISS** - Keep It Simple, Stupid (no over-engineering)
- **Clean Code** - читаемый, тестируемый, поддерживаемый код

**Процессы разработки:**
- Итеративная разработка с четким планом (tasklist.md)
- Автоматизированный контроль качества (make quality)
- Тесты перед рефакторингом
- Документация как часть кода (docstrings, type hints)
- Code review перед merge

**Готовность к разработке:**
Все разделы технического видения согласованы и готовы для использования. Проект следует лучшим практикам Python разработки и может быть расширен дополнительными возможностями по мере необходимости без нарушения качества кода.

**Специализация через роли:** ⭐ **НОВОЕ**
Система ролей через файловые промпты позволяет легко создавать специализированных ассистентов для конкретных задач (техподдержка, код-ревью, консультации). Каждая роль - это отдельный файл в `prompts/`, что упрощает создание, тестирование и распространение специализированных конфигураций.

**Баланс качества и простоты:**
Проект использует современные инструменты контроля качества (Ruff, Mypy, pytest-cov), но сохраняет простоту архитектуры и минималистичный подход. Качество кода не достигается за счёт сложности - все решения остаются простыми и понятными.
